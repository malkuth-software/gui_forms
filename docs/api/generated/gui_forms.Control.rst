gui_forms::Control
==================

.. cpp:namespace:: gui_forms

.. cpp:class:: Control : public Component, public std::enable_shared_from_this<Control>, public ControlCapabilities<Control>

   ``#include <gui_forms/control/control/control.hpp>``

   The base class of every visual element: geometry, visibility, input and a place in the tree.

   Every stock control derives from :cpp:class:`Control <gui_forms::Control>`, so the properties, events and
   methods on this page apply to all of them. A control has a permanent
   :cpp:class:`StableId <gui_forms::StableId>`, a parent and children, requested bounds that a layout turns into
   arranged bounds, visibility and enablement, focus and tab order, and paint
   and hit-test routines. Create controls with ``make_control``, arrange them
   under a root, and hand the root to a :cpp:class:`Window <gui_forms::Window>`, which lays them out, routes
   input to them and paints them. Derive from :cpp:class:`Control <gui_forms::Control>` yourself to make a
   custom control; override ``measure``, ``arrange`` and ``on_paint``, and call
   :cpp:func:`invalidate <gui_forms::Control::invalidate>` from your setters.

   :Parameters:

      **stable_id** : ``StableId``
         Identity of the control, unique within its window. Logs, automation and
         semantic actions address the control by this ID.

         stable ID's string. Setting it raises :cpp:func:`name_changed <gui_forms::Control::name_changed>`.

         raises :cpp:func:`visible_changed <gui_forms::Control::visible_changed>`.

         Whether the control accepts input. A disabled control is painted

         disabled with it. Setting it raises :cpp:func:`enabled_changed <gui_forms::Control::enabled_changed>`.

         a write (``auto_size = true``) changes it and raises :cpp:func:`auto_size_changed <gui_forms::Control::auto_size_changed>`.

      **causes_validation** : ``bool``, default ``true``

         have focus instead, unless a placeholder is set. Empty by default, and
         empty text never shows. It must be valid UTF-8, or
         ``std::invalid_argument`` is thrown. It is bindable and published as the
         semantic field ``tool_tip``. Data items such as list rows have none.

         base dock and anchor layout ignores it; auto-size measurement and scroll
         extents include its right and bottom parts. Values must be finite and
         nonnegative.

      **padding** : ``Insets``, default ``{0, 0, 0, 0}``

         Anchored children keep their distances to these padded edges when the

         backmost docked child takes the outermost edge.

      **anchor** : ``AnchorStyles``, default ``AnchorStyles::top | AnchorStyles::left``

         when the parent resizes. Anchored to both left and right, the control

      **justify_self** : ``SelfAlignment``, default ``SelfAlignment::automatic``

         stock panel: :cpp:class:`GridPanel <gui_forms::GridPanel>` still takes each child's alignment from its

      **align_self** : ``SelfAlignment``, default ``SelfAlignment::automatic``

      **auto_size_mode** : ``AutoSizeMode``, default ``AutoSizeMode::grow_only``

      **layout_direction** : ``LayoutDirection``, default ``LayoutDirection::inherit``

         parent is left to right. Right to left mirrors docking, anchoring and
         requested bounds, as Windows Forms' ``RightToLeftLayout``: the layout is
         computed left to right and mirrored about the control's viewport, so

         The background and foreground colours the application authored for this control (WinForms' BackColor and ForeColor), or none: the theme's colours stand. They are the T4-1 authored colours of the control's parts (PartPaint::authored_background and authored_foreground), with the same rules: a part's own authored colour, the most specific, stands over them; the theme's important declarations stand over them; forced high contrast drops them; and a disabled part keeps the theme's disabled colours, so disabled text stays greyed. - The background paints the control's bounds before its content, as WinForms' OnPaintBackground does, and fills the control's grounds (faces, wells, plates) flat, keeping their borders. - The foreground draws the control's text, marks and rules. They reach what a control paints through paint_part; a control that draws its own text or surfaces directly reads ambient_back_color and ambient_fore_color. Ambient inheritance, as WinForms: a control without its own colour takes its nearest ancestor's (ambient_back_color, ambient_fore_color), so a colour set on a container flows to every descendant that sets none. An inherited background is not painted again over the bounds (the ancestor already painted it) and does not fill a well: an editor's or a list's well keeps the theme's window colour, as WinForms' text and list boxes keep SystemColors.Window under a coloured form. A check box's box is a well too: it keeps the theme's colour under an inherited background, but the check box's own background fills it, where WinForms' box stays white. Writing one (std::nullopt clears it) repaints the control and its descendants. This control's own colour, else its nearest ancestor's, else none.

   :Events:

      **name_changed** : ``Event<const std::string&>``
         Raised after :cpp:member:`name <gui_forms::Control::name>` changes, with the new name.

      **visible_changed** : ``Event<bool>``
         Raised after :cpp:member:`visible <gui_forms::Control::visible>` changes, with the new value. Hiding or showing an

      **enabled_changed** : ``Event<bool>``
         Raised after :cpp:member:`enabled <gui_forms::Control::enabled>` changes, with the new value.

      **right_to_left_changed** : ``Event<bool>``

Every affected control's resolved value is updated first; then the events run an ancestor before its descendants and siblings in painter order, each after that control is marked arrange, paint and hit-test dirty. A handler may write directions or move controls: the nested change announces its own controls, and a control it already announced is not announced again.

         The WinForms mouse events (owner's mouse-event rule, 2026-11-08). The window raises them on the UI thread in WinForms' order: MouseDown, then on the release over the control the same button pressed Click and MouseClick (or, for a press the host counted as the second of a double-click on a control with ControlStyles::standard_double_click, DoubleClick and MouseDoubleClick), then MouseUp. Both need ControlStyles::standard_click, as in WinForms; a primary Click is followed by on_activate. MouseEnter, MouseHover (once per entry, after the pointer rests within the hover rectangle for the hover time) and MouseLeave follow the pointer; MouseCaptureChanged is raised on the control losing the capture. The events are kept in a record made by the first accessor called, so a control nobody listens to stores none.

   .. rubric:: Notes

   A parent owns its children; a child refers to its parent weakly. Keeping your
   own ``std::shared_ptr`` to a control is allowed and keeps it alive after it is
   removed. Create controls with ``make_control<T>(StableId, ...)``, which returns
   a ``std::shared_ptr``; tree operations need the control to be owned by one.

   A control that is attached to a window belongs to that window's UI thread.
   Every setter and tree operation on it from another thread throws
   ``std::logic_error``, changes nothing, and counts in
   ``MetricsSnapshot::rejected_wrong_thread_operations``. A detached control has no
   UI thread yet, so the check applies only once it is attached. Disposed
   controls reject every setter with ``std::logic_error``; their getters still
   work.

   Setters store the value, record what it invalidates, and then raise the
   change event. Setting the current value again does nothing and raises
   nothing. Input events such as ``ButtonBase::clicked`` are raised only by input
   and by explicit ``perform_click``, never by setters.

   Hiding or disabling a control, or one of its ancestors, removes focus from
   the subtree (nothing is focused afterwards), releases its pointer capture and
   press, and closes overlays and focus scopes it owns. The window's
   ``control_availability_changed`` is raised, then the control's own
   :cpp:func:`visible_changed <gui_forms::Control::visible_changed>` or :cpp:func:`enabled_changed <gui_forms::Control::enabled_changed>`.

   Between :cpp:func:`begin_init <gui_forms::Control::begin_init>` and :cpp:func:`end_init <gui_forms::Control::end_init>`, change events are coalesced by event:
   each is raised once, in the order of its first change, with the latest value.
   A property changed and changed back inside the transaction still raises its
   event once. Use the transaction to configure a control in several steps
   without handlers seeing intermediate states.

   Disposing a control revokes its own connections and queued work, releases
   its tag, bindings and theme override, detaches it from its window and its
   parent, and then disposes its children. Disposing a control inside one of
   its own event handlers is allowed. Removing a child does not dispose it.

   .. rubric:: Examples

   Lay out a button anchored to the bottom-right corner, and see it follow the
   corner when the window grows:

   .. code-block:: cpp

      std::shared_ptr<gf::Panel> root = gf::make_control<gf::Panel>(gf::StableId("dialog"));
      std::shared_ptr<gf::Button> ok = gf::make_control<gf::Button>(gf::StableId("dialog.ok"), "OK");
      (*ok).set_bounds({300.0, 200.0, 80.0, 28.0});
      (*ok).anchor = gf::AnchorStyles::right | gf::AnchorStyles::bottom;
      (*root).add_child(ok);

      gf::Window window(root, gf::Size{400.0, 240.0});
      gf::Rect before = (*ok).arranged_bounds();   // {300, 200, 80, 28}
      window.resize(gf::Size{500.0, 300.0});
      gf::Rect after = (*ok).arranged_bounds();    // {400, 260, 80, 28}
      static_cast<void>(before);
      static_cast<void>(after);

   A custom control with its own property. The setter rejects disposed or
   wrong-thread use, ignores equal values, and asks only for a repaint:

   .. code-block:: cpp

      class Swatch final : public gf::Control {
      public:
          explicit Swatch(gf::StableId stable_id) : gf::Control(std::move(stable_id)) {}

          gf::Color color() const { return color_; }
          void set_color(gf::Color color) {
              require_mutable();
              if (color == color_) return;
              color_ = color;
              invalidate(gf::Dirty::paint);   // no layout is needed
          }

          void on_paint(gf::Painter& painter, gf::Rect) override {
              painter.fill_rect(client_rectangle(), color_);
          }

      private:
          gf::Color color_ = gf::Color::rgba(0, 120, 215);
      };

      void example() {
          std::shared_ptr<Swatch> accent = gf::make_control<Swatch>(gf::StableId("theme.accent"));
          (*accent).set_bounds({0.0, 0.0, 48.0, 24.0});
          gf::Window window(accent, gf::Size{48.0, 24.0});
          window.perform_layout();
          (*accent).set_color(gf::Color::rgba(200, 40, 40));
      }

      The background and foreground colours the application authored for this control (WinForms' BackColor and ForeColor), or none: the theme's colours stand. They are the T4-1 authored colours of the control's parts (PartPaint::authored_background and authored_foreground), with the same rules: a part's own authored colour, the most specific, stands over them; the theme's important declarations stand over them; forced high contrast drops them; and a disabled part keeps the theme's disabled colours, so disabled text stays greyed. - The background paints the control's bounds before its content, as WinForms' OnPaintBackground does, and fills the control's grounds (faces, wells, plates) flat, keeping their borders. - The foreground draws the control's text, marks and rules. An inherited background is not painted again over the bounds (the ancestor already painted it) and does not fill a well: an editor's or a list's well keeps the theme's window colour, as WinForms' text and list boxes keep SystemColors.Window under a coloured form. A check box's box is a well too: it keeps the theme's colour under an inherited background, but the check box's own background fills it, where WinForms' box stays white.

Control and component
=====================

The base classes every control and nonvisual component derives from, with layout, docking, anchoring and validation vocabularies (layout constraints, intrinsic sizes and layout direction among them), and the anatomy each control publishes: named parts, part roles and states, and the interactions each type raises.

.. list-table::
   :class: autosummary longtable
   :widths: 35 65

   * - :cpp:class:`Component <gui_forms::Component>`
     - The base class for everything whose lifetime GUI.Forms tracks.
   * - :cpp:class:`Control <gui_forms::Control>`
     - The base class of every visual element: geometry, visibility, input and a place in the tree.
   * - :cpp:class:`StableId <gui_forms::StableId>`
     - The permanent name of a control, unique within its window.

.. cpp:class:: ContentRegion final

   ``#include <gui_forms/control/content_region/content_region.hpp>``

   A control's content region (property-capabilities study, decision 10): the control owns its chrome (frame, headers, scroll bars), the region its items' lazy pending set. note_item records an item whose paint changed and, on the first entry since the last gather, asks the owner's window to gather the region after its next layout. The owner's Control::gather_content_regions then turns each pending item into damage at the item's final geometry and calls clear_pending. A redraw of the whole owner (Control::redraw_all) folds the region instead: fold_pending drops the entries, which would damage rectangles about to move anyway. The owning control holds the region as a member; the region observes its owner and is used only on the owner's UI thread.


   .. rubric:: Construction

   .. cpp:function:: ContentRegion(Control& owner, std::size_t capacity) noexcept

      Up to ``capacity`` items are kept pending (at least one); the storage is reserved at the first note, the region's only allocation. Past the capacity the region asks for a paint of its whole owner instead.


   .. rubric:: Properties

   .. cpp:function:: std::span<const ContentItemKey> pending() const noexcept

      The items noted since the last gather or fold, in note order. An item noted twice in a row is kept once; one noted twice apart is kept twice, and its rectangle is damaged twice (the same union).


   .. rubric:: Methods

   .. cpp:function:: void note_item(ContentItemKey item, Dirty kinds)

      Records that ``item`` changed with ``kinds``. Paint is gathered lazily; any other kinds (semantics, hit test, layout) go to the owner's Control::invalidate at once. A detached or initializing owner, or a region past its capacity, gets Control::invalidate(Dirty::paint) instead of an entry. May throw (the first note's reservation, the window's pending list) before anything is recorded.

   .. cpp:function:: void clear_pending() noexcept

      The gather's end: drops the entries; the storage stays.

   .. cpp:function:: Dirty fold_pending() noexcept

      The redraw-all's fold: returns Dirty::paint when anything was pending (or the region had overflowed) and drops the entries, drawing nothing.

.. cpp:var:: constexpr std::size_t maximum_control_tree_depth

   The deepest a control tree may nest, in levels, the root counted as one: a root with one child is two levels deep. Control::add_child and Control::insert_child (and through them the form loader, the static-tree builder and the C ABI's insert_child) refuse with ControlTreeDepthError, before changing anything, an attachment whose target's depth plus the attached subtree's height would pass it. A window or overlay root is attached at level one, so every tree it can take is within the limit. The stack budget (house rule, owner 2026-11-11: recursion over runtime-shaped data needs an enforced depth): the walks over the tree that still recurse once per level (layout, paint, hit testing, semantic publication, focus order, disposal) run on the window's root thread. The smallest such stack the supported hosts give is a macOS secondary thread's 512 KiB; Windows' main thread reserves 1 MiB, macOS and Linux main threads 8 MiB. Half of 512 KiB, 256 KiB, is given to the deepest recursive walk, at 4 KiB per level: layout recurses through several frames per level (the root's measure pass, the container's layout engine, the child's measure override), each a few hundred bytes, and 4 KiB leaves room for an application override's own frame. 256 KiB at 4 KiB per level is 64 levels. (A sanitizer build's larger frames run on the 8 MiB main threads of macOS and Linux.) Win32 itself copes badly with child windows nested past about 50, so no Windows Forms layout relies on deeper trees. Destruction does not recurse per level (Control::release_children_iteratively).
